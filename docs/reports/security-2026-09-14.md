## Findings, ordered by deployment priority

### S1 — High priority, open: outdated production web runtime

Location: `web/Dockerfile:8`, `deploy/images.env`. The pinned Caddy 2.11.4 image
contains a Go 1.26.3 binary, older Go dependencies and older Alpine packages.
Updating GATI's own Go toolchain does not rebuild this upstream executable.
Binary scanning confirms affected standard-library functions are present, including
HTTP serving and URL resolution. Upstream describes a header-timeout bypass when
unencrypted HTTP/2 support is enabled and quadratic relative-path resolution.
These are examples requiring configuration/reachability assessment, not claims
that this review reproduced an Internet exploit against GATI.
[HTTP timeout advisory](https://pkg.go.dev/vuln/GO-2026-6089),
[URL complexity advisory](https://pkg.go.dev/vuln/GO-2026-6218).

Many package findings concern bundled tools or features the current Caddyfile does
not use. The current origin is private and has header/body/time limits, but those
controls do not justify blanket dismissal of vulnerable server dependencies.
Remediate before public launch: prefer an available maintained upstream image with
patched dependencies; otherwise make an explicitly pinned, reproducible Caddy build
with patched Go/modules and a minimal patched runtime. Re-scan the actual result,
triage each remaining finding and re-run production ingress/browser/rollback checks.
Do not simply add an unversioned `apk upgrade` or suppress every scanner result.

A separate Caddy advisory names 2.11.5 as the fix for a `forward_auth` plus
`reverse_proxy` connection-selection bug. GATI does not configure `forward_auth`,
so this path appears inapplicable. During this review the GitHub release API still
returned 2.11.4 as latest and the 2.11.5 release lookup returned 404. An advisory's
fixed-version field is not evidence that a consumable image exists. Verify an
actual artifact and digest before proposing that upgrade.
[Caddy advisory](https://github.com/caddyserver/caddy/security/advisories/GHSA-6365-7ppr-5r92).

### S2 — Medium priority, open triage: tunnel dependency inventory

Location: `compose.production.yaml` tunnel image and `deploy/images.env`.
The cloudflared 2026.9.1 image has package advisories in x/crypto, gRPC, libc and
zlib. Its Go binary scan finds no affected symbols, so the three high-severity
package matches are not three demonstrated GATI vulnerabilities. This result
also does not analyze native libc/zlib code. Two libc findings have a fixed Debian
package version in the inventory; other findings have no scanner-listed fix.
For example, consult the [Debian CVE-2026-5450 record](https://security-tracker.debian.org/tracker/CVE-2026-5450).

Before launch, obtain a refreshed supported image if available or document precise
non-applicability/mitigation for remaining findings, with image digest, rationale,
owner and review deadline. Avoid an indefinite whole-image exception. Keep the
connector's network and capabilities restricted, and validate the real tunnel
separately; no Cloudflare authentication was available for this review.

### S3 — Medium priority, fixed: running release verification missed launch drift

Location: `scripts/release.py`, regression cases in `scripts/test_release.py` and
`scripts/rehearse-release.py`. The previous verifier could accept the expected
image while missing changed startup arguments (including proxy trust), environment,
user, extra read-only configuration mounts or extra network attachments. It also
ignored an existing tunnel or dedicated worker omitted by new profile flags;
Compose does not automatically stop those services.

The verifier now compares these launch settings, image defaults, memory/CPU/PID
bounds, bind/tmpfs mounts, network attachments and reserved proxy addresses. It
refuses activation/verification with an unselected live tunnel or worker. Failures
do not echo environment values or secrets. Unit tests reject these mutations; an
actual owned stack test attaches web to the private backend network, observes
rejection, disconnects it and passes verification again.

This is protection against observable deployment drift. An attacker already
controlling the host or Docker daemon can evade it. Host firewall/network policy,
external tunnel configuration and provider controls still require inspection.

### S4 — Low priority, fixed in CI: application dependency audits were manual

`make security-check` now runs both govulncheck and npm audit, and CI invokes it.
The local run passes. This covers application dependencies, not upstream binaries
or OS packages in release images; full image scans remain a separate release gate.
The added CI step has been run locally, not on a remotely pushed workflow.

## Deployment plan and next steps

1. **Close runtime findings locally.** Resolve S1 and triage S2. Rebuild the exact
   runtime images; retain fresh scan/SBOM evidence, including justified exceptions.
   Add full image auditing to the release process. No credentials are needed for
   this work. Do not publish the current artifact merely because tests pass.
2. **Freeze and independently verify a new release.** Commit the final fixes,
   prepare for the selected hostname, scan all four exact images, repeat production
   proxy/browser/two-API and release-switch tests and compare independent clean
   builds to the actual image binaries/browser bytes. Arrange independent security
   review before the public pilot, and keep public claims limited to the evidence.
3. **Choose the operational inputs.** Select a domain, VPS/budget, operator contact,
   private security-reporting channel and private alert destination. An initial
   single-host 4-vCPU/8-GiB pilot candidate follows the measured local headroom;
   benchmark the actual host before promising capacity. Begin with one combined
   API/worker plus Valkey, Caddy and tunnel; add two API replicas only when measured
   request demand warrants it. One host/Valkey remains a failure boundary.
4. **Prepare the authorized VPS privately.** Use SSH keys, current host/container
   patches, restricted management access, no inbound application/store ports,
   disabled swap/hibernation/core dumps/RAM snapshots and no participant logging or
   backups. Transfer the new immutable artifact and compare its separately retained
   manifest hash. Provision secrets directly on the host, never in chat or Git.
   Run preflight and private activation/verification before connecting the edge.
5. **Configure and test the actual Cloudflare zone/tunnel.** Follow the
   [runbook](../DEPLOYMENT.md) and the
   [official named-tunnel setup](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/).
   Route only the selected hostname to `http://web:8080`, with unmatched hosts
   rejected. Enforce HTTPS; verify origin isolation, header spoof resistance and
   edge rate limits. Cache only allowlisted public assets/releases and always
   bypass authenticated requests. Test expiry and failure responses; default cache
   behavior is insufficient for this API's privacy rules.
   [Cloudflare cache behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/).
6. **Run a capped pilot after explicit public authorization.** Verify the complete
   Albanian journey on actual Android/iOS browsers, expiry/cancel/retry, late joining,
   arrival and coarse public maps. Leave push disabled initially unless separately
   tested and enabled by the user. Use private bucketed monitoring, memory/worker-lag
   alerts and voluntary usability feedback, without participant analytics. Check
   rollback, loss-of-store behavior and recovery before widening access.

For the human-controlled steps, provide only the chosen hostname, hosting/budget
preference, access method and contact/alert choices. Arrange SSH/Cloudflare login
privately when needed. Repository publication and public deployment require explicit
user authorization; local commits do not authorize either action.

The accepted limits remain: device location can be fabricated, multiple credentials
can belong to one person, public/private aggregate information permits some inference,
and Cloudflare/privileged providers can observe traffic or live memory. Reproducible
artifacts do not prove remote operator honesty. These are documented boundaries,
not problems that a clean dependency scan would solve.
